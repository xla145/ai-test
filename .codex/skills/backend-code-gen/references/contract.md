# 业务契约与跨层映射

在生成前，把需求和源码中已确认的事实汇总为一份字段与操作定义，各层代码均从这里推导。它是生成工作的共同依据，不要求引入新 DSL、代码生成框架或额外审批。

## 如何记录

- 已有设计文档或接口定义：直接引用并补足本次差异，不再维护一份重复规格。
- 单个字段/接口：在当前实施说明中列明变化即可。
- 新模块或多实体：用下面的字段表和操作表组织信息；只在项目有约定或用户要求时落为独立文件。
- 数据库现状、接口兼容要求、用户新需求存在冲突时，指出具体差异。字段含义、归属或更新语义不清楚时先澄清，不按模板猜测。

## 字段定义

记录本次涉及的字段；复用现有公共审计字段约定，不必每次重抄。

| 信息 | 要回答的问题 |
|---|---|
| 名称与含义 | Java 字段、JSON 名、数据库列名是什么？是否为派生字段？ |
| 类型与范围 | Java/SQL 类型、字符串长度、数值精度、单位或时区是什么？ |
| 可空与默认 | 创建时必填吗？数据库允许 null 吗？默认值由哪一层提供？ |
| 读写范围 | 创建/修改可传吗？列表/详情返回吗？谁有权设置？ |
| 更新语义 | 未传、null、空串/空集合分别表示保留、清空还是非法？ |
| 约束与关系 | 枚举取值、唯一性范围、关联归属、索引和删除规则是什么？ |
| 来源 | 用户需求、现有表结构或哪个源码实现？哪些仍是假设？ |

### 示例：名称字段最多 100 字符

以下仅用于说明映射方式，不给实际业务自动添加字段。

已确认契约：`name` 为 String，创建必填、不允许纯空白、最大长度 100；数据库列为 `name VARCHAR(100) NOT NULL`，无默认值；创建和完整编辑允许修改，列表及详情可返回。

| 产物 | 应体现的内容 |
|---|---|
| Entity | String name，列映射与当前 ORM 约定一致 |
| 新增 BO / 完整编辑 BO | @NotBlank、@Size(max = 100)，接口字段说明同步写明限制 |
| 查询 BO | 仅在需求要求名称筛选时添加；不沿用新增的必填约束 |
| VO | 仅在对应操作需要时返回；不复制写入校验注解 |
| SQL | VARCHAR(100) NOT NULL；已有列先核实存量数据和兼容性，再设计迁移 |
| Service | 按契约映射 name，不额外截断或 trim，除非需求已有明确规则 |
| 验证 | 非空边界与长度边界；若允许补充平面字符，核对 Java 长度与数据库字符计数差异 |

部分更新的 name 若“未传保留、显式 null 非法”，不能直接复制完整编辑 BO 的 @NotBlank，也不能仅凭普通 nullable String 区分缺失和显式 null；沿用项目的字段存在性表达，并验证这两种请求。空集合清空关联等规则同理。

## 操作定义

每个实际需要的操作记录：HTTP 方法与路径、请求/响应、权限与数据范围、业务前置条件、写入字段、事务范围、失败行为。只读操作无需填写无关的事务/写入项。

例如状态转换需明确“允许的原状态 → 目标状态”，从契约推导带原状态和归属条件的更新，并检查影响行数；不让客户端通过普通 edit 任意写 status。

主键、审计人、租户等系统控制字段即使在 Entity 中存在，也不自动进入可写 BO。密码、内部路径等字段也不因实体存在就进入响应。

## 一致性检查

生成后沿字段和操作各追踪一遍，而非只逐文件检查语法：

1. 从请求字段追踪到校验、Service 映射、实体与 SQL，确认长度/精度、单位、可空与默认策略协调一致。
2. 从操作追踪到 Controller、Service、Mapper 条件与响应，确认权限、删除过滤、事务和错误行为没有漏层。
3. 修改契约时列出受影响的产物；没有结构变化就不生成迁移，没有接口变化就不扩展 BO。
4. Java 初始化默认值不等于数据库默认值；BO 可选不等于数据库可空；响应字段也不必与实体一一对应。每个差异应有业务原因。

现有模板提供代码形态；契约决定字段、接口与行为。遇到模板示例不一致时按契约和当前源码适配，不反过来修改业务需求。
