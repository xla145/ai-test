# 页面整体美化

以真实业务内容建立清晰、有辨识度的界面，兼顾信息密度和操作效率。当前项目 AIProbe 面向 AI 生成测试用例、脚本与回归执行；设计应帮助用户快速识别当前项目、测试对象、执行进度和结果。

## 确定范围与现状

- 用户只要求先创建技能时，完成技能即可；用户要求执行美化时，继续完成实现和验证。
- 从真实页面、入口组件、共享样式及依赖确定技术栈，不套用其他项目的目录或组件库。遵循仓库 AGENTS.md；存在 `.codegraph/` 时，先使用 CodeGraph 定位代码。
- 页面可访问时先观察当前界面，记录主要区域、关键操作与视觉问题。浏览器地址以当前运行信息为准，不固定端口。
- 收到截图或浏览器区域批注时，先把圈选区域与当前页面对应起来。用户说“鸡肋”“这块也是”时，结合上下文检查重复信息、低价值区域和操作层级，不只改颜色、圆角或缩小字号。先简述具体改法，再实施已授权的调整。
- “整个页面”覆盖导航、页头、主要内容、辅助面板以及该页面的弹窗和状态；不要自行扩大到所有路由。修改共享样式时检查受影响页面。
- 保留业务含义、数据绑定、事件与可操作入口。界面预览缺少后端时如实说明，不把虚构统计数据写进产品。

## 形成设计方向

开始实现前，用简短说明明确当前最影响体验的问题、拟采用的视觉方向和重点调整区域。已有品牌规范或用户参考图优先；未指定风格时根据产品用途自行选择，无需把常规设计决策交回用户。

AIProbe 默认适合克制、精确的工具型界面：中性背景、明确的主操作、适中的信息密度，依靠排版、对齐与状态反馈建立层次。具体色相、明暗主题和布局需结合当前界面决定，不强制统一成某一种模板。

整体改版或用户要求去除 AI 味时，读取 [设计系统与逐层打磨](references/design-system-and-craft.md)，先完成其中的现状审视、产品方向与设计变量映射。局部调整只使用相关条目，不为了套用流程重做整个页面。

按问题严重程度决定改动幅度：跨布局、配色、文案的系统性问题才做整体调整；少量问题保留原有方向做局部修正；界面已经成熟时不要为了制造差异而替换品牌或布局。优先解决不可读、不可操作、焦点丢失、遮挡与溢出，再处理装饰细节。

## 实现重点

### 布局与信息层级

- 先判断一个区域是否值得存在，再决定如何美化。检查同一项目名、品牌说明、路径和操作是否在顶部、侧栏与正文反复出现；保留有不同任务价值的信息，合并仅重复上下文的入口。
- 优先修正阅读顺序、区域比例、对齐和留白，再处理装饰。区分页面标题、分区标题、数据正文与辅助说明。
- 主操作位于稳定且易发现的位置；次要操作降低强调。操作密集区域可分组，但不隐藏高频入口。
- 卡片用于表达独立内容关系，避免每段文字都套卡片或多层嵌套边框。工具栏、列表和日志可用分隔线与背景层次组织。
- 长名称、路径、日志和代码提供合理换行、截断后的完整查看或局部滚动；避免页面整体横向溢出。

涉及标题栏、侧栏、项目切换或下拉菜单时，读取 [导航与信息精简](references/navigation-and-density.md)。其中记录本项目已经验证的设计取舍和原生窗口检查点；具体尺寸是参考，不是所有项目的固定模板。

### 视觉系统

- 优先复用、整理现有设计变量，再补充语义化的背景、表面、边框、正文、弱文本、强调色和状态色。将通用调整落实在共享变量或组件，避免零散覆盖。
- 审查 CSS、内联样式和工具类中的硬编码值，按组件逐批映射到现有变量；只改变量定义并不能覆盖未引用变量的样式。按已安装样式库版本实现，不建立并行主题系统。
- 使用有限的字体层级与一致的间距节奏；中文采用适合阅读的系统字体栈，代码和日志采用等宽字体。无需仅为装饰引入远程字体。
- 圆角、控件高度、描边、阴影和图标尺寸保持一致。阴影用于表达浮层或层级；渐变、玻璃效果和高饱和色仅在设计有明确理由时使用。
- 复用已有图标库，同一区域保持线条风格一致。不要用 emoji 代替产品操作图标。
- 图像应服务内容与品牌；测试工具界面不为填充空间添加无关插画或宣传式大幅区域。

### 可用性与状态

- 覆盖 hover、focus-visible、active、selected、disabled、loading、empty 和 error 中实际涉及的状态。键盘焦点清晰，图标按钮有可访问名称。
- 状态同时用文字或图标表达，不只依赖颜色。普通文本对比度以 WCAG AA 的 4.5:1 为基准，大文本及关键非文本边界按相应标准检查。
- 让空状态解释当前情况并提供真实可用的下一步；错误状态给出可执行的处理方式。不要为美化移除必要的错误信息。
- 动效用于解释切换和反馈，短而克制，并尊重 prefers-reduced-motion。已有明暗主题均需保持可读性，不擅自增加主题功能。
- 按实际使用环境检查窗口缩放；桌面工具优先保证常用桌面与窄窗口可用，Web 页面再覆盖移动端。断点由内容容纳需求决定。

## 工程与验证

- 遵循现有框架、组件和样式组织方式；Vue 工作使用可用的 vue-best-practices 技能。除非现有能力确实不足，不增加 UI 框架或大体积依赖。
- 先统一页面骨架与共享视觉，再处理局部细节；不借视觉改版重写无关业务逻辑。
- 修改前识别已有未提交改动，增量编辑并保留其他工作。移动组件后检查旧样式与选择器是否仍有调用，避免叠加已失效的布局规则。
- 使用仓库已有的相关类型检查或构建命令。纯样式改动以实际渲染验证为主；交互逻辑变更运行相应测试。
- 用可用浏览器工具检查修改后的真实页面，至少覆盖主要视图、一个较窄窗口和本次涉及的关键交互；有弹窗、菜单、加载或错误状态时按实际可触发条件检查。
- 比较修改前后视觉，检查对齐、拥挤、遮挡、滚动区域、浮层层级和文本可读性；发现问题后修正。无法打开页面时明确区分静态检查与未完成的视觉验收。
- 交付时简述视觉变化、涉及文件、已完成的验证及实际限制。能提供真实截图或运行预览时展示结果，不把编译成功等同于视觉验收通过。
- 每轮采用当轮实际验证结果，不沿用上一轮的“全部通过”。测试失败需报告具体项；只有检查过失败涉及的代码及改动范围，才能说明它与本轮改动无关。浏览器预览不能代替 Electron 原生标题栏、拖动区和窗口按钮验收。

## 来源与适用边界

本技能结合 [UI UX Pro Max](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill) 的设计系统与检索方法，以及 Damir Sokolovsky（[@heydamir](https://x.com/heydamir)）的 [Unslop](https://heydamir.design/unslop) 逐层打磨方法。Unslop 的改编内容依 [CC BY 4.0](https://creativecommons.org/licenses/by/4.0/) 标注来源；具体改编与来源链接见上述参考文件。

本技能提供独立可用的提炼规范，不等同于安装 UI UX Pro Max 的搜索引擎或资源库。外部设计建议服从用户要求、当前品牌、实际平台与可访问性约束；不照搬其默认框架、图标库、营销页布局或审批流程。
