## 1. 背景与目标

当前接口测试主要围绕“从文档生成用例 → 审核 → 生成脚本 → 回归”展开。用户导入接口后，缺少直接查看接口定义、填写参数、发送请求和保存有效用例的入口。

本方案采用以下主线：

> 导入接口 → 调通单接口 → 保存并审核单接口用例 → 编排业务场景 → 统一回归 → 定位失败。

目标用户为需要验证接口及业务流程的测试人员和开发人员。

核心目标：

- 导入完成后，用户可以直接选择接口、填写参数并发送请求。
- 调试请求与正式测试用例分开，避免临时操作自动进入回归。
- 将多个请求编排为有顺序、有传值、有业务断言的完整场景。
- 保留现有脚本回归能力，普通执行不依赖模型。
- 将接口定义、测试数据和执行版本关联起来，便于接口更新后的影响检查。

非目标：第一版不建设通用低代码流程平台，不包含性能压测、接口 Mock、任意脚本编程平台和复杂流程画布。

## 2. 现有能力与缺口

以下结论基于当前代码检查，后续实现仍需对具体行为补充验证。

| 领域 | 当前能力 | 本次需要补齐 |
| --- | --- | --- |
| 文档解析 | 支持 OpenAPI / Swagger 文件及 HTTP/HTTPS 地址 | 接口定义持久化、导入预览、差异更新 |
| 用例生成 | 按接口约束生成基线用例；可由 agent 补充 | 从“导入即生成”改为按接口选择生成和去重 |
| 单接口执行 | 已有请求描述及 pytest/httpx 执行能力 | 请求编辑器、临时调试、请求历史、保存为用例 |
| 多接口流程 | `api_flow` 顺序执行、提取变量、多角色 | 步骤编辑器、变量选择器、前置校验、清理步骤 |
| 断言 | HTTP 状态码、响应结构、字段相等、数据库校验 | 可视化编辑和结果展示，逐步扩充断言运算符 |
| 环境鉴权 | 环境配置、默认凭据、角色账号、接口登录 | 在新工作台中复用，明确覆盖关系 |
| 回归范围 | 按用例选择执行，支持保存测试集 | 区分单接口用例与业务场景，统一入口 |
| 执行报告 | 已有回归结果、失败信息和报告导出 | 每步请求响应、断言、变量及执行版本明细 |

需要特别处理的兼容点：当前 `shared_vars` 是 session 级 fixture，允许不同用例之间传值；新方案默认要求场景之间隔离，不能只改页面而沿用原行为。

## 3. 核心概念与操作流程

### 3.1 概念区分

| 对象 | 含义 | 示例 |
| --- | --- | --- |
| 接口定义 | 描述接口的请求及响应契约，不代表测试已通过 | `POST /orders` |
| 调试请求 | 用户临时编辑并发送的一次请求配置 | 手工填入商品和数量，查看响应 |
| 单接口用例 | 固定请求数据及预期结果，可重复验证 | 商品不存在时拒绝创建订单 |
| 业务场景 | 多个请求组成的一条完整测试用例 | 创建订单 → 查询 → 取消 → 再查询 |
| 测试集 | 一组用例或场景的执行范围，不隐含数据依赖 | 订单冒烟、核心回归 |
| 执行记录 | 特定版本在特定环境中的执行结果 | 测试环境的一次订单冒烟 |

一个接口可以关联多条单接口用例，也可以被多个业务场景步骤使用。业务场景不能简单等同于勾选多个接口后批量执行。

### 3.2 推荐流程

```mermaid
flowchart LR
    A[导入并确认接口定义] --> B[选择接口并调试]
    B --> C[保存单接口用例]
    C --> D[审核并发布执行版本]
    B --> E[编排业务场景]
    D --> E
    E --> F[试运行并审核场景]
    D --> G[加入测试集或直接回归]
    F --> G
    G --> H[查看报告与定位失败]
```

这是推荐操作顺序，不要求所有单接口用例全部通过后才能创建业务场景。场景可以先保存为草稿，再补齐数据和断言。

## 4. 页面与导航设计

将接口相关能力收敛到“接口测试”入口，内部采用四个页签：

| 页签 | 主要任务 | 主要操作 |
| --- | --- | --- |
| 接口管理 | 维护接口目录和文档版本 | 导入、搜索、查看差异、查看影响 |
| 单接口测试 | 调试请求和维护单接口用例 | 发送、编辑断言、保存用例、生成用例 |
| 业务场景 | 编排多个请求的业务测试 | 添加步骤、传值、切换角色、试运行 |
| 回归执行 | 选择范围、执行、查看本次结果 | 选择用例或测试集、执行、打开报告 |

项目级环境、角色账号和鉴权配置继续共用。不要在每个页签重复维护一套凭据。

现有“用例库”保留为跨测试类型的统一审核入口；接口工作台与用例库指向同一条用例记录。现有“测试报告”保留为全部执行历史入口。

页面之间支持带上下文跳转：接口 → 关联用例 → 引用场景 → 执行记录。返回时保留项目、接口、环境和筛选状态；切换项目时清理不属于新项目的选择。

## 5. 接口管理与导入

### 5.1 导入流程

1. 选择 OpenAPI / Swagger 文件或填写规范文档地址。
2. 解析文档，展示标题、版本、模块和接口列表。
3. 预览新增、变更、未变化及来源文档中已移除的接口。
4. 用户确认导入范围和更新内容。
5. 保存接口定义及导入版本，进入接口目录。
6. 用户按需调试或生成测试用例，不默认生成全量用例及脚本。

文档无法解析时展示错误位置或原因，不写入半份接口目录。普通文档页面地址与 JSON/YAML 规范地址需要明确区分；获取不到有效规范时提示修正地址。

### 5.2 目录与详情

- 按文档来源、标签或业务模块组织接口。
- 支持名称、路径、方法搜索，以及“有无用例”“待检查”等筛选。
- 详情展示请求参数、必填约束、响应结构、示例及关联资产。
- 文档示例仅作为请求初始值，不视为真实可用测试数据或已验证预期。

### 5.3 重复导入与影响检查

- 接口拥有稳定内部 ID；在项目和来源范围内，默认以规范化的 `method + path` 匹配，`operationId` 作为辅助信息。
- 不同来源定义相同接口时提示冲突并选择处理方式，不静默覆盖。
- 方法或路径变更默认表现为新增和移除候选，可由用户确认映射关系。
- 文档中消失的接口标记“来源已移除”，不直接删除其用例和历史记录。
- 参数、响应结构和鉴权发生变化时，展示受影响的用例及场景，标记“待检查”。
- 更新接口契约不得覆盖人工设置的请求参数、业务断言和提取规则。
- 对已有接口重复生成基线用例时，按接口及生成规则识别重复项，提供新增或预览更新，不无限追加。

## 6. 单接口测试

### 6.1 页面结构

```text
┌──────────────┬─────────────────────────────────────────┐
│ 接口目录     │ 环境 / 角色 / 方法 / 请求地址            │
│              │ [发送请求] [保存为用例] [生成用例]       │
│ 订单         ├─────────────────────────────────────────┤
│ · 创建订单   │ Params / Headers / Body / 断言 / 提取变量│
│ · 查询订单   ├─────────────────────────────────────────┤
│ · 取消订单   │ 响应内容 / 耗时 / 断言结果 / 请求历史    │
└──────────────┴─────────────────────────────────────────┘
```

窄窗口时将请求与响应改为上下布局，保留发送和保存操作可见。

### 6.2 请求调试

第一阶段支持路径参数、Query、Header 和 JSON Body，与现有执行器能力对齐；暂不在界面提供执行器不支持的文件上传、表单或二进制 Body 选项。

- 环境决定 Base URL，接口定义提供相对路径。
- 默认继承环境鉴权，也可选择角色或明确关闭鉴权，支持未登录用例。
- 修改参数后直接发送，不要求先保存、审核或生成整套脚本。
- 发送前检查环境、必填输入、JSON 语法和变量引用。
- 鉴权头来源冲突时明确提示最终采用哪项配置，避免手工 Header 被静默覆盖。
- 支持超时配置和取消；取消后不继续调度，但提示服务端可能已经处理请求。
- 调试历史记录实际请求和结果，允许恢复参数，但不自动创建测试用例。

需要资源 ID 的接口允许填写已知数据，或配置显式前置步骤；前置步骤需可查看、可追踪，不能在后台隐式调用其他接口。

### 6.3 保存用例与生成用例

“保存为用例”保存名称、优先级、请求配置、断言、数据准备及来源接口版本，初始为草稿。修改已有用例时保留稳定 ID 并更新修订版本。

“生成用例”支持选择正常、必填缺失、边界、类型和鉴权等范围。确定性规则优先，AI 补充业务用例作为单独入口并提示模型用量。

文档不足以推导的业务码、权限规则和预期字段标记为待补充。不能把当前响应自动当成正确答案；从响应创建断言后需要用户确认。

### 6.4 断言设计

| 类型 | 示例 | 交付阶段 |
| --- | --- | --- |
| HTTP 状态码 | 状态码为 200 | 第一阶段 |
| 字段相等 | `code` 等于 `0` | 第一阶段 |
| 响应结构 | 字段类型符合指定结构 | 第一阶段 |
| 存在、非空、包含、数值比较 | `data.orderId` 非空 | 第一阶段 |
| 数据库校验 | 订单记录存在且状态正确 | 复用现有能力，第二阶段完善界面 |
| 跨步骤字段比较 | 查询订单编号等于创建结果 | 第二阶段 |

第一版沿用点号路径，例如 `data.items.0.id`，不宣称支持完整 JSONPath。显示值和编辑器应区分字符串、数字、布尔值和空值。

无断言时可以调试并保存草稿，但不能审核为正式回归用例。只有状态码断言时提示业务验证可能不足。用例审核状态、规范检查状态和最近执行结果分别展示，不能用“已审核”代替“已通过”。

## 7. 多接口业务场景

### 7.1 编辑方式

第一版采用可排序的步骤列表。每步可折叠和展开，支持添加、复制、移动、禁用与删除；不建设复杂拖拽流程画布。

步骤可从接口目录或已有正向用例添加，复制配置快照并保留来源信息。新增普通步骤应优先使用正常请求模板，不自动混入负向用例的异常参数和预期。

### 7.2 场景示例：创建订单后取消

| 步骤 | 请求 | 参数与提取 | 断言 |
| --- | --- | --- | --- |
| 1 | 创建订单 | 输入商品与数量；提取 `orderId` | 业务成功，编号非空 |
| 2 | 查询订单 | 使用 `${orderId}` | 编号一致，状态为待支付 |
| 3 | 取消订单 | 使用 `${orderId}` | 取消成功 |
| 4 | 再次查询 | 使用 `${orderId}` | 状态为已取消 |

### 7.3 步骤配置

每步配置名称、来源接口及版本、角色、请求数据、断言、提取变量和超时。场景可定义默认角色，步骤按需覆盖。

如需前置数据准备和执行后清理，应使用单独区域，明确与正式业务断言的区别。登录等通用认证继续复用项目鉴权；仅在登录本身是被测行为时放入业务步骤。

### 7.4 变量规则

- 场景输入参数、场景变量、环境变量分层管理，凭据使用受控引用。
- 普通名称引用优先级为：已提取场景变量 → 场景输入参数 → 环境变量；角色鉴权独立解析，不作为普通变量任意覆盖。
- 同一场景内提取变量名默认唯一，重名时提示修改，避免无意覆盖。
- 变量选择器显示来源步骤、字段路径和预期类型。
- 后续步骤只能引用场景输入、环境变量及此前有效步骤已提供的变量。
- 删除、移动或禁用步骤后重新检查引用；无效引用阻止执行并定位到字段。
- 整个字段使用 `${orderId}` 时保留原始类型；嵌入文本时转换为字符串。
- 每次场景运行建立独立变量上下文，不向其他用例和场景传播。

### 7.5 失败、清理与重跑

- 普通业务步骤失败后停止后续业务步骤，依赖步骤标记“阻塞”，不伪装成通过。
- 清理步骤在正常结束或业务失败后都尝试执行；缺少必要变量时记录无法执行的原因。
- 清理失败单独报告，不能覆盖最初业务错误；若业务通过而清理失败，本次仍不得显示为全部通过。
- 对创建、支付、退款等请求不默认重试，避免重复副作用。
- 第一版支持整场景重跑。仅重跑某一步、恢复历史变量和断点续跑留待后续设计。
- 试运行允许草稿执行，并明确标注调试结果；正式回归只使用已审核的执行版本。

## 8. 回归执行与报告

### 8.1 测试范围

支持分别选择单接口用例、业务场景及已保存测试集。测试集保存用例或场景的稳定 ID，不依赖显示名称，也不隐含执行顺序和变量共享。

执行前展示环境、请求地址、角色、范围及预计执行条数。空选择不退回全量执行。已废弃、未审核、版本待检查或缺少可执行配置的项目，列明原因并阻止作为正式回归项执行。

业务场景内部顺序执行；第一版不同用例和场景默认串行，后续再引入有边界的并发与测试数据隔离。

### 8.2 执行状态与报告

用例结果区分通过、失败、执行错误、跳过、阻塞和取消。HTTP 请求正常返回但断言不满足属于失败；网络超时、变量解析错误等作为执行错误记录。

业务场景整体作为一条用例统计，步骤另外统计；避免一个四步场景在通过率中被重复算成四条用例。

报告记录：

- 执行 ID、项目、环境、开始结束时间和执行版本。
- 用例或场景结果、步骤结果、耗时、失败原因。
- 脱敏后的实际请求、响应、断言预期与实际值。
- 提取变量及其来源，敏感值仅显示脱敏内容。
- 数据准备、清理及数据库校验结果。
- 脚本版本或可执行配置摘要，用于解释“本次到底执行了什么”。

执行器本身不调用模型。AI 用于用例或场景草稿生成，以及失败分析；失败分析是否自动触发应沿用并明确展示项目配置，不能把执行零模型调用表述为整个流程必然零成本。

## 9. 数据模型与版本管理

以下为逻辑模型建议，不要求每项独立建表；应结合现有 SQLite 和 workspace 存储实现。

| 实体 | 关键字段 | 作用 |
| --- | --- | --- |
| 接口来源 ApiSource | ID、项目、来源类型、地址或文件标识、内容摘要 | 记录文档归属，来源地址不得保留明文凭据 |
| 导入批次 ApiImport | ID、来源 ID、时间、差异、结果 | 追踪一次导入与更新 |
| 接口定义 ApiDefinition | 稳定 ID、来源、方法、路径、模块、当前修订 | 构建接口目录 |
| 接口修订 ApiRevision | 接口 ID、修订号、请求与响应定义、内容摘要 | 保留历史契约和差异 |
| 单接口用例 TestCase | 现有用例字段、接口 ID、来源修订、请求、断言、自身修订 | 复用统一用例库 |
| 业务场景 TestCase | 现有用例字段、输入参数、有序步骤、清理步骤、自身修订 | 继续以一条用例承载场景 |
| 场景步骤 ApiStep | 稳定步骤 ID、顺序、来源引用、请求快照、断言、提取 | 支持编辑和报告定位 |
| 测试集 ApiTestSet | 项目、名称、用例或场景 ID 列表 | 管理回归范围 |
| 调试记录 DebugRun | 项目、接口、环境、请求快照、结果、时间 | 与正式回归记录区分 |
| 执行快照 RunSnapshot | 用例及场景版本、接口修订、环境非敏感摘要、执行配置 | 固定本次执行内容 |

版本规则：

1. 接口契约、用例配置、脚本分别有版本，不能只依赖某一份当前文件。
2. 用例或场景发生执行相关修改后，回到待审核状态；旧执行记录继续指向旧版本。
3. 接口更新只标记影响，不自动替换场景步骤快照；确认同步后重新检查和审核。
4. 正式回归在启动时冻结执行快照，运行期间的编辑只影响之后的执行。
5. 测试集在执行前解析到当时已审核的版本并冻结，不在运行途中读取最新编辑内容。

## 10. 技术落地与兼容

### 10.1 保留现有架构

沿用 React + TypeScript + Ant Design、Electron IPC、主进程编排、Python 引擎和 pytest/httpx，不引入独立 HTTP 测试服务。

```text
接口工作台
    ↓ Electron IPC
编排层：环境、鉴权、执行范围、快照
    ↓ Python 引擎
统一请求执行器：渲染 → 请求 → 断言 → 提取 → 结果
    ├─ 临时调试：直接执行一份请求快照
    └─ 正式回归：由数据驱动脚本调用相同执行逻辑
```

调试和回归共用请求、鉴权与断言语义，避免页面发送成功但脚本失败。HTTP 请求由引擎执行，不从 renderer 直接发送，以复用鉴权和规避浏览器跨域限制。

### 10.2 模块改造建议

| 位置 | 调整方向 |
| --- | --- |
| `desktop/src/renderer/pages/ApiPage.tsx` | 从生成入口改为接口工作台容器，拆分目录、请求编辑器和结果面板 |
| `desktop/src/renderer/pages/RunPage.tsx` | 复用执行范围与结果能力，接入工作台回归页签 |
| `desktop/src/renderer/pages/CasesPage.tsx` | 与接口用例、业务场景共享编辑和审核结果 |
| `desktop/src/shared/ipc.ts`、preload、主进程 IPC | 新增接口导入预览、定义查询、调试、场景保存和执行协议 |
| `desktop/src/main/orchestrator.ts` | 拆分导入、生成、调试和回归，避免导入自动生成全套脚本 |
| `engine/aitest/openapi.py`、`cli.py` | 扩充完整接口定义输出、导入差异及按接口生成能力 |
| `engine/aitest/models.py`、`store.py` | 增加接口资产、来源引用、修订与执行快照 |
| `engine/aitest/apigen.py`、请求执行模板 | 共用执行逻辑，新增断言、变量隔离、结构化步骤结果和清理机制 |
| `engine/aitest/api_selection.py` | 兼容现有测试集，增加状态与版本有效性检查 |

### 10.3 旧资产兼容

- 现有 `api` 继续对应单接口用例，`api_flow` 继续对应业务场景，不重建两套用例库。
- 旧用例缺少来源接口时允许继续查看和按原版本执行，标记“未关联接口定义”，支持后续人工关联。
- 不因方法和路径相同就自动合并旧用例；同一接口本就允许有多个测试条件。
- 旧测试集继续按稳定用例 ID 加载，对失效引用给出明确提示。
- 对依赖 session 级跨用例变量的旧资产，保留明确标识的旧执行配置并提示迁移；新建用例默认隔离，依赖链应迁移为同一个业务场景。
- 修改执行模板后，不静默改写历史执行；重新生成并审核新版本后应用新语义。

## 11. 非功能要求

- 凭据继续通过系统钥匙串或现有受控注入方式获取，不保存进用例、脚本、workspace 或报告。
- 日志、历史和导出统一脱敏；处理 Header、Query、Body 和响应中的敏感信息，不能仅隐藏 Authorization。
- 生产环境沿用现有显式确认机制；单接口调试和业务场景试运行同样适用，不能绕过回归页已有约束。
- 定义导入失败不得部分更新；保存动作失败不得把界面误标为已保存。
- 导入和执行过程显示进度、失败原因及可重试动作；错误不清空用户未保存的参数。
- 请求历史设置保留数量、响应体大小上限和清理策略；超大响应截断展示并明确标记。
- 导入、变量渲染、断言、状态聚合和兼容迁移需要针对性测试；页面验证覆盖从导入到回归的实际闭环。

## 12. 实施阶段与验收标准

需求优先级：P0 为当前阶段交付必需；P1 为后续增强。阶段顺序是依赖顺序，不代表已承诺工期。

| 阶段 / 编号 | 优先级 | 交付内容 | 验收标准 |
| --- | --- | --- | --- |
| 第一阶段 API-01 | P0 | 接口导入和目录 | 文件或地址导入可预览并持久化；同一文档再次导入不重复新增接口；失败不留下部分更新 |
| 第一阶段 API-02 | P0 | 单接口调试 | 可选择环境和角色、编辑参数并直接发送；响应、状态码、耗时可见；不自动生成用例 |
| 第一阶段 API-03 | P0 | 用例与断言 | 一次有效调试可保存为草稿、审核并进入回归；支持多条用例；参数修改会触发重新审核 |
| 第一阶段 API-04 | P0 | 基线生成与现有回归衔接 | 可按接口和规则生成草稿；重复生成有去重策略；已有已审核用例仍可执行 |
| 第二阶段 API-05 | P0 | 场景编辑与传值 | 可完成四步订单取消场景，引用前序响应编号，调整步骤后识别无效引用 |
| 第二阶段 API-06 | P0 | 角色、隔离与清理 | 场景内可切换角色；两个场景使用同名变量不串值；失败后清理仍尝试，原始失败保留 |
| 第二阶段 API-07 | P0 | 场景试运行与审核 | 草稿可试运行；关键步骤失败后依赖步骤阻塞；只有已审核版本进入正式回归 |
| 第三阶段 API-08 | P0 | 统一回归范围与测试集 | 可混合选择单接口和场景；空选不跑全量；保存再加载测试集保持成员一致 |
| 第三阶段 API-09 | P0 | 步骤报告与执行快照 | 可定位具体失败请求和断言；执行中编辑不影响本次结果；历史可识别执行版本 |
| 第三阶段 API-10 | P0 | 更新影响与兼容验证 | 契约变更能列出引用资产；旧用例和测试集迁移后可继续使用；旧跨用例依赖有明确兼容路径 |
| 后续 API-11 | P1 | AI 场景草稿、并发、更多请求类型 | 在顺序执行及数据隔离稳定后单独设计验收 |

每阶段都应交付可运行闭环；接口更新的基本差异检测和“待检查”标记从第一阶段建立，第三阶段完善跨场景影响分析，不留到最后才处理覆盖风险。

## 13. 边界与待确认事项

本方案按以下默认选择编写，可在实施评审时调整，无需阻塞文档交付：

1. 第一版优先支持 OpenAPI/Swagger 和 JSON 请求；若实际主要使用表单、文件上传或特殊签名，应调整第一阶段范围。
2. 第一版场景使用有序列表，暂不支持条件分支、循环、场景嵌套和断点续跑。
3. 手工创建接口、cURL 导入、Postman 集合导入作为后续扩展，不纳入当前导入验收。
4. 角色、环境、凭据和用例审核复用现有项目机制，不另建权限体系。
5. 请求历史的默认保留数量、响应大小上限以及导入规模指标，实施前依据实际项目规模确定并写入配置与验收记录。
6. 本方案不预估固定工期；在确认首批接口样本、鉴权方式及迁移资产数量后再拆分任务和估算。
