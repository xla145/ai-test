# UI 前置条件检查清单设计

日期：2026-11-15
状态：设计补充，尚未实现原子检查项执行门禁
适用范围：通用 UI 测试平台，不在框架中定义模型、渠道或业务字段规则。

## 1. 当前缺口

当前覆盖检查以原始 preconditions 数组索引为单位。一条复合条件即使只关联一个断言，也可能通过结构检查；系统无法据此判断该断言是否证明句子中的全部事实。已有登录检查、条目覆盖和脚本确认指纹继续保留。

本设计将条件原文、检查计划、录制证据和单次运行结果分开。关联数仅表示追溯关系，不能代表满足程度。

## 2. 页面与交互

工作台前置条件改为可展开的“执行前检查”面板，放在正文步骤之前。

收起时显示：执行前检查 · 6 项 · 2 满足 / 1 不满足 / 3 未检查。没有本次运行时显示“尚未检查”，不能沿用历史绿色状态。

展开内容：

| 检查内容 | 要求 | 本次实际值 | 状态 | 证据 |
| --- | --- | --- | --- | --- |
| 当前执行身份 | 用例要求的角色 | 来自本次会话验证 | 满足 / 不满足 | 会话检查及身份验证步骤 |
| 数据对象及属性 | 原文声明的限制 | 页面/API/数据库只读证据 | 满足 / 不满足 / 无法验证 | 对象标识、断言步骤、截图或读取结果 |

上方提供“查看原文”和“检查计划 / 本次结果”切换，下方展示阻断原因与真实可用操作。

- 检查计划：展示拆分项、原文引用、检查方法、关联断言；未运行时标为“已编排”，不显示满足。
- 本次结果：展示执行时间、环境、角色、脚本版本和每项实际结果。历史结果单独标记，不影响本次状态。
- 点击证据：定位到对应脚本步骤，查看期望、实际值和来源；敏感字段脱敏。
- 发现漏项：通过现有“让 AI 修正”入口补充检查计划。修改计划后原验证与确认失效，必须重验。
- 脚本未生成：可展示拆分计划及缺项；不能假装已有执行结果。
- 窄窗口：每项上下排列要求、实际值、状态和证据；不靠横向滚动承载完整表格。

不新增重复编号：列表以检查内容为标题，P1.1 等技术 ID 仅在证据详情中显示。

## 3. 拆分和审核

转换阶段输出 preconditionChecks。保留原始 preconditions 原文，原始索引从 1 开始；每个检查项引用原文中的一个或多个完整片段，禁止将原文重写成更容易通过的条件。

每个检查项应只有一个可判定的事实：对象、字段/身份/数量、比较要求、观察范围和证据获取方式。对象不存在时依赖该对象的检查项标记阻断，不重复搜索。

- 不按逗号机械拆分，避免拆坏比例、集合及逻辑关系。
- “A 且 B”分别验证；“A 或 B”保留原逻辑，不擅自要求全部满足。
- 原文没有明确值、范围或判断规则时标记待澄清，不补业务默认值。
- “多个对象”必须保留查询范围，不能用筛选后单页行数或只看到一行推断整体。
- 角色会话有效不自动证明权限等级；身份或权限需要对应证据，不能仅依据角色名称。
- 原文数字按原语义比较，不把要求 3:1 自动简化为看见两个数字。

结构验证确保每个原始条件有检查项、引用有效、ID 唯一、依赖无环。结构验证不能证明拆分语义完整：页面须保留原文与计划供用户核对，AI 的语义审核只能提示疑似遗漏，不能提供“数学保证”。

## 4. 数据模型

执行计划新增字段示意：

```json
{
  "preconditionChecks": [
    {
      "id": "P1.1",
      "sourceIndices": [1],
      "sourceQuotes": ["原文中的完整要求"],
      "statement": "单个可验证事实",
      "expected": "保留原始值及逻辑的要求",
      "method": "session|ui|api|database|manual",
      "dependsOn": [],
      "verificationHint": "观察位置与判定方式；未知 DOM 时不虚构选择器"
    }
  ]
}
```

所有原文声明的条件默认必需。不能通过 required=false 绕过；确需修改要求时走用例编辑并失效旧计划。

录制步骤增加 preconditionCheckIds，与原有 preconditionIndices 并存；保存时校验检查 ID 来自当前计划、只能绑定有效证据/断言，不接受任意字符串补项。一次检查可以包含多个必要断言，所有必要断言成功才能满足。

运行结果独立保存：runId、checkId、planHash、scriptHash、env、role/sessionId、status、expected、actual、evidence、reason、startedAt、finishedAt。预期和实际值可为有类型的 JSON；超长内容截断，凭据不落盘。

状态集合：not_checked、checking、satisfied、unsatisfied、unverifiable、blocked。自动验证与人工确认的证据来源分开记录。取消或执行器异常不得把 checking 转为 satisfied。

## 5. 执行门禁

完整回放顺序：恢复指定会话 → 只读导航与前置检查 → 汇总门禁 → 正文操作 → 预期断言。

导航、打开详情等检查所需动作允许出现在前置阶段，但不能假借检查修改数据。仅靠动作名无法识别业务副作用，检查计划必须明确只读意图；未知副作用时阻断，不能自动点击。

- 每次完整回放重新执行检查，不使用探索时的满足状态。
- 任一必要项不满足、无法验证或被依赖阻断，正文不运行，结果归为前置条件阻断，不归为产品缺陷。
- 检查失败保留实际值和证据；其余项可按依赖继续只读检查，汇总缺口。
- 人工项默认阻断自动回放。人工确认必须绑定本次运行、环境、对象、角色与证据；如果系统暂不支持绑定，应保持无法验证，不能转成常量 true。
- 清单或脚本变化、角色/环境变化时旧确认失效；执行中途切换会话须重新检查依赖会话的条件。
- 单步调试允许观察和定位问题，但跳过前置检查的调试不能认证脚本。
- 前置检查与正文之间仍可能发生外部状态变化。重要对象状态可在写入前再断言，但不宣称整个过程具备事务隔离。

探索阶段本身也执行前置门禁，不能等保存脚本时才发现未验证：检查计划绑定工具会话；完成必要检查前，正文阶段切换必须被拒绝。该约束需要工具级状态机，不能只依赖提示词。

## 6. 数据准备边界

检查、准备、复查是三个不同动作。默认只检查，不修改环境以迎合用例。

存在用户声明的准备配方时，使用原有数据准备能力，记录执行和清理结果；无配方时展示缺失条件、实际值和需准备的数据，不推断允许创建、改权重或切换配置。执行准备之后必须重新检查。权限规则沿用现有授权范围。

## 7. 工程落点与实施次序

1. contract.ts / uiContractPrompt：增加清单模型、原文引用和结构验证，升级合同缓存策略，历史合同重新转换。
2. BrowserSession / tools.ts：绑定当前用例检查计划、检查 ID 和证据，加入前置阶段与正文阶段状态机；重置/切换用例时清理状态。
3. coverage.ts / codegen.ts：逐检查项完整性验证，生成独立前置阶段；固定对应模型或数据标识仍属于用例资产。
4. runner / engine store / reports：持久化逐项执行结果与证据，正文未运行时保持阻断，禁止通过重试覆盖原始缺口。
5. UiWorkflow / ScriptSteps / UiWorkbench：显示清单和本次结果；纳入指纹、确认门禁和旧版本迁移。

以上需成闭环交付，不能只上线提示词或列表。旧脚本保留，标明“未包含逐项前置检查，需重新生成/验证”，不得按现有断言数量猜测迁移。

## 8. 验收场景

- 复合条件拆出多项，只验证其中一项：不能进入正文或确认。
- 所有关联齐全但一项实际值不符：正文零执行，报告前置条件阻断。
- 缺少原文引用、伪造检查 ID、遗漏条件、依赖环：拒绝计划或保存。
- 查到目标但属性不符：不换目标，不自动修改数据。
- 会话有效但身份无法证明：不把登录有效等同角色权限满足。
- 计划/环境/角色变化、取消运行：旧状态不能认证本次。
- 前置项依赖失败：依赖项显示阻断原因，不报一串无关定位失败。
- 一次完整通过后再次运行时环境发生变化：重新检查并正确阻断。
- 窄窗口显示完整要求和证据入口，无重复编号和横向溢出。
