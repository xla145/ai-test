2. 六大核心问题

P0 Prompt 膨胀：规则堆积导致 token 浪费与模型注意力稀释 Token 消耗 效果差

现象：explorePrompt() 单个函数生成 ~15KB 文本（约 5000+ token），包含 47 条内联规则。uiContractPrompt() ~8KB，包含 26 条规则。许多规则是对同一语义的反复强调：

// prompts.ts 中重复出现 ≥3 次的规则模式： "不要换数据" / "不擅自创建或替换数据" / "不能用相近数据替代" "不要遍历系统管理菜单" / "不要在代码库查找" / "不要用 shell 翻看" "停止" / "立即停止" / "停止并报告" / "阻塞" (出现 20+ 次) "角色精确匹配" / "不使用名称相近的角色替代" (3 处) "不要虚构" / "不能臆造" / "不用第一行替代" (5 处)

根因：规则是追加式写入的——每次发现 agent 犯一个新错误，就加一条禁止规则。但这些规则并没有降低出错率，因为：

  • 模型的注意力在 5000+ token 的规则海洋中被稀释，越重要的规则越可能被淹没
  • 否定式规则（"不要 X"）比肯定式规则（"必须 Y"）消耗更多 token 且效果更差
  • 规则之间存在矛盾（例如同时要求"不虚构 target"和"必须提供 target 或 targetHint"）

影响：每条用例多消耗 ~3000-5000 个无效 token；模型不遵守规则不是因为没看到，而是因为规则太多无法全部满足。

P0 合约转换 + 修复 = 两次完整 prompt 发送 Token 消耗 速度慢

现象：合约转换失败时，修复 prompt 把整个 uiContractPrompt（8KB）连同上一轮的完整输出和错误信息重新发送：

// uiTesting.ts:148-153 const repairPrompt = [ "这是一次受限的结构修复...", `上一轮输出：${converted.message}`, // 完整的 JSON 输出 (~2-5KB) `校验错误：${(conversionError).message}`, uiContractPrompt(brief, roles, ...), // 再发一次完整 8KB prompt ].join("\n");

根因：没有使用结构化输出（Structured Output / JSON Schema constrained decoding）。模型自由输出 JSON，格式错误只能靠事后校验 + 整轮重试。

影响：转换失败率（文档称"revision 9 补全"说明至少迭代了 9 次）意味着大量用例要走两轮，每轮 ~15KB，合计 ~30KB prompt token + 两次模型调用的延迟。

P0 Prompt 与 Skill 模板双重维护、语义冲突 效果差 维护成本

现象：explorePrompt() 中写"规则以本提示为准"（line 59），但 ui-explore.md 仍然包含 50 行独立规则。两处规则存在分歧：

// prompts.ts line 59: "已给出，不必再调用 case-store.list_cases， 也不必再读 .agents/skills/ui-explore.md，规则以本提示为准" // 但 ui-explore.md 仍有独立于 prompts.ts 的内容： // 如"完整回放门禁"章节的 expect_observed/expect_number 规则 // 这些规则不在 explorePrompt 中

根因：Prompt 演化路径分叉——prompts.ts 和 ui-explore.md 是两个独立维护的规则源。explorePrompt 试图用"以本提示为准"覆盖 skill 文件，但 agent 实际上可能仍会读到 skill 文件。

影响：agent 收到矛盾指令时行为不可预测。某些只在 skill 文件中的规则不生效，某些 prompt 中的新规则被 skill 文件中的旧规则覆盖。

P1 探索阶段每次工具调用都执行 Guard 持久化 速度慢

现象：在 tools.ts:139，每次工具调用结束时都执行 guard.persist()，即把完整的前置检查状态 + 所有已录制步骤序列化为 JSON 写磁盘：

// tools.ts:137-140 } finally { const current = states.get(ctx)?.guard; current?.persist( ctx.session.recording().length ? ctx.session.recording() : savedSteps.get(ctx)?.steps ?? [] ); }

根因：为了在进程崩溃时不丢证据，选择了最保守的持久化策略。

影响：一条用例探索期间有 30-80 次工具调用，每次都序列化并写入一个不断膨胀的 JSON 文件。随着录制步骤增多，每次写入的数据量从几百字节增长到几十 KB。累计 IO 开销可观。

P1 stillCurrent() 双重执行 + 重复拉取 速度慢

现象：在 uiTesting.ts 中，stillCurrent() 被调用两次（探索前 line 206、探索后 line 217），每次都重新拉取项目配置、角色列表、数据配方列表并计算指纹：

// uiTesting.ts:199-206 — 每次 stillCurrent() 执行： const latest = await this.uiCase(projectId, env, caseId, ...); // 拉用例 const latestProject = await this.services.project(projectId); // 拉项目 const latestRoles = await this.deps.engine([ "list-roles", "--project", projectId ]); // 拉角色 const latestData = await this.deps.engine([ "list-test-data", "--project", projectId ]); // 拉数据配方 // 然后计算 sha256 指纹对比

根因：防止用例在转换/探索期间被修改导致脏数据，但实现方式是全量重新拉取而非增量校验。

影响：每次 stillCurrent() 调用 4 次 engine 子进程 + 1 次 SHA-256 计算。两次调用 = 8 次子进程 + 2 次哈希。这是纯粹的防御性开销。

P1 缓存指纹过度敏感，命中率低 速度慢 Token 消耗

现象：缓存指纹包含 11 个维度，任何一个变化都会使缓存失效，触发完整的 AI 转换：

// uiExecutionContract.ts:30-31 this.fingerprint = sha256(JSON.stringify(canonical({ revision: REVISION, // 转换规则版本 projectId, // 项目 env, // 环境名 caseId, // 用例 ID source: { title, steps, expected, // 用例内容 preconditions, data_refs, // 前置/数据 available_data, // 数据配方目录 ← 任何配方变化都失效 capabilities // 验证能力 }, roles: [...roles].sort(), // 全部角色 ← 新增无关角色也失效 environment, // 完整环境配置 ← 改 login 也失效 selectedRole, // 选择的角色 dataFingerprint // 数据配方脚本摘要 })));

根因：指纹设计过于保守。roles 包含所有配置角色而非用例关联角色；environment 包含完整环境配置而非合约相关字段；available_data 在新增无关配方时也变化。

影响：在活跃开发的项目中，缓存几乎总是失效。每次失效 = 一次完整 AI 转换（8KB prompt + 模型调用）。

3. 优化方案：按 ROI 排序

优化原则：不动架构大手术，先把投入产出比最高的改动做了。下面按"节省 token / 提速效果 × 实现难度的倒数"排序。

🔴 优化 1：Prompt 瘦身 — 规则合并、去重、结构化

预估收益 ↓ 50-60% prompt token

做法：

  1. 将 47 条规则压缩为 ~15 条结构化指令。用肯定式（"必须"）替代否定式（"不要/不能/禁止"）。例如：
    // BEFORE: 5 条分散规则 "不擅自创建或替换数据" "不能用相近数据替代" "不要遍历系统管理菜单" "不替换测试数据或削弱断言" "不要在代码库或文件里查找账号" // AFTER: 1 条结构化规则 "数据来源：只使用用例声明的 data_refs 和 valueRef 变量。 缺失时报告阻塞（data_blocked）。"
  2. 将规则分层：核心规则（5 条）放在 prompt 顶部；边界规则（10 条）放在 prompt 底部的 "constraints" 块中。消除 skill 文件与 prompt 的重叠。
  3. 删除 ui-explore.md 中与 explorePrompt 重复的内容，只保留 explorePrompt 中明确引用的补充规则。

预估：explorePrompt 从 ~15KB → ~6KB，uiContractPrompt 从 ~8KB → ~3.5KB。每条用例节省 ~8000 token。

风险：低。规则精简后需要在 3-5 个典型用例上验证 agent 行为没有退化。

🔴 优化 2：结构化输出 — 消除合约修复轮次

预估收益 ↓ 1 次 AI 调用 / 失败用例

做法：

  1. 从 executionContractSchema（Zod schema）自动生成 JSON Schema，作为 AI 调用的 response_format 传入。Claude API 支持 tool_use 或 json_schema 模式的结构化输出。
  2. 结构化输出保证返回的 JSON 一定符合 schema，完全消除格式修复轮次。
  3. 语义校验（如 sourceQuotes 必须匹配原文）仍由 validateExecutionContract() 执行，但格式永远不会出错。
// 当前方式：自由输出 → 解析 → 校验 → 失败则修复 agentTask("ui_contract", uiContractPrompt(...)) → JSON.parse(message) → validateExecutionContract() → 失败？→ agentTask("ui_contract_repair", ...) // 又一轮 // 优化后：结构化输出 → 格式保证正确 → 只做语义校验 agentTask("ui_contract", prompt, { response_format: { type: "json_schema", schema: contractJsonSchema } }) → validateExecutionContract() // 只校验语义

预估：消除 ~40% 的合约转换失败（格式问题占比），节省修复轮的 ~15KB prompt token 和一次模型调用延迟。

这正是文档 §18 末尾提到但标注"尚未实现"的内容。

🟡 优化 3：缓存指纹收窄 — 提高命中率

预估收益 缓存命中率 ↑ 2-3×

做法：

  • roles：只纳入用例关联角色（即合约中实际引用的 role），而非全部配置角色
  • environment：只纳入 base_url + databases 存在性 + data_api 存在性，不纳入 login 细节
  • available_data：只纳入用例的 data_refs 关联项，新增无关配方不影响指纹
// BEFORE: 11 维完整指纹 { revision, projectId, env, caseId, source: {...全部}, roles: 全部角色, environment: 完整环境配置, selectedRole, dataFingerprint } // AFTER: 只纳入影响合约输出的维度 { revision, projectId, env, caseId, source: { title, steps, expected, preconditions, data_refs }, roles: 用例引用的角色, capabilities: { database: bool, dataApi: bool }, selectedRole, relatedDataFingerprint: 只有 data_refs 关联项的摘要 }

风险：中。需验证收窄后不会复用过时的合约。建议保留 versionFile 机制作为安全网。

🟡 优化 4：Guard 持久化降频

预估收益 IO 次数 ↓ 80%

做法：

  1. 只在状态变化时持久化：前置检查通过/失败、case_step 推进、阻塞、录制步骤变化
  2. 其余工具调用（snapshot、find_text、navigate 等只读操作）不触发 persist
  3. 添加 dirty 标记，只有标记为 dirty 时才实际写入
// BEFORE: 每次工具调用都 persist } finally { current?.persist(steps); } // AFTER: 只在状态变化时 persist } finally { if (current?.dirty) { current.persist(steps); current.dirty = false; } }

🟡 优化 5：stillCurrent() 轻量化

预估收益 子进程调用 ↓ 6 次/用例

做法：

  1. 首次调用时缓存项目配置、角色列表和数据配方的哈希值
  2. stillCurrent() 改为比较哈希而非重新拉取全部数据：用 engine 提供一个 fingerprint 子命令，在 Python 侧计算并返回单个哈希
  3. 探索前的 stillCurrent() 可以去掉——合约刚转换完成，用例不可能在毫秒内变化

🟢 优化 6：探索上下文裁剪 — 合约 JSON 瘦身

预估收益 探索 prompt ↓ 20-30%

现象：在 explorePrompt 中，完整的 contract JSON 被 JSON.stringify 内联：

// prompts.ts:71 ...(contract ? ["已转换的执行用例：", JSON.stringify(contract), ...] : caseBlock),

做法：

  • 移除合约 JSON 中的 sourceQuotes（已在原始用例中）
  • 移除 verificationHint（agent 已有页面上下文）
  • 只传 steps[].actions 和 preconditionChecks[].id/method/runtime/paramRefs
  • 将 JSON 改为紧凑格式而非缩进格式

按"实施难度 × 收益"排序，建议分三批落地：
